# Архитектура (Phase 1 baseline)

```
image ──► preprocessing ──► layout / line detection ──► OCR/HTR (Arabic script) ──► raw_ocr
              (configurable)      (backend-specific:            │
                                   kraken BLLA, Paddle DB,      ├─► [Phase 4] Old Tatar → modern Tatar (diplomatic / modernized)
                                   VLM page-level)              └─► [Phase 5] modern Tatar → ru / ba
```

Реализовано только то, что нужно для честного baseline: предобработка, адаптеры OCR, сегментация
строк, нормализация для метрик, метрики, раннер бенчмарка, отчёты. Транскрипция и перевод —
только зарезервированные поля в схеме результата.

## Модули

| путь | ответственность |
|---|---|
| `src/ocr/base.py` | `OCRBackend.recognize(PIL.Image) -> OCRResult`, `OCRResult`/`OCRLine`, `BackendUnavailable` |
| `src/ocr/registry.py` | имя → адаптер (ленивый импорт), лицензия, коммерческая применимость, причина недоступности |
| `src/ocr/*_backend.py` | адаптеры: Paddle, EasyOCR, Tesseract, Kraken (+OpenITI/PP-OCRv6), Phoenix, CHURRO, Azra, Transkribus-заглушка, dummy |
| `src/ocr/model_store.py` | загрузка весов по URL с проверкой checksum и докачкой |
| `src/layout/` | сегментация строк kraken BLLA (+кэш), RTL-порядок для box-детекторов |
| `src/preprocessing/` | EXIF → документ → перспектива → crop → deskew → resize → контраст → (бинаризация, выкл.) |
| `src/text/arabic_normalization.py` | `source_preserving_text` vs `normalize_for_evaluation` (профили правил) |
| `src/evaluation/` | метрики, раннер (`python -m evaluation.evaluate`), скоринг, отчёт, воспроизводимость |
| `src/benchmark/` | стандарт манифеста + валидация (утечки между сплитами), конвертер Wikisource → GT |
| `src/pipeline/` | склейка стадий для CLI; схема результата с `raw_ocr`/`corrected_ocr`/`modern_tatar`/`translation` |
| `cli.py` | `models`, `ocr`, `benchmark`, `report` |

## Ключевые решения

### 1. Единый интерфейс `OCRBackend` + реестр с ленивым импортом
* **Выбрано:** абстрактный класс с `recognize(image) -> OCRResult`; общая логика (ленивая загрузка, тайминг,
  гигиена текста, агрегирование уверенности) в базовом классе; адаптеры реализуют `_load`/`_recognize`.
  Реестр хранит `module:Class` строкой и импортирует модуль только при использовании.
* **Альтернативы:** прямые вызовы библиотек из раннера; плагины через entry points; отдельный сервис на модель.
* **Почему:** остальная система не знает о конкретных моделях; отсутствие одного пакета (paddle, kraken,
  llama.cpp) не ломает остальные — бэкенд просто сообщает `unavailable: <причина>`.
* **Риски:** несовместимые зависимости в одном окружении (сейчас: kraken хочет `click<8.3`, `safetensors~=0.7`,
  а paddlex/transformers ставят новее; на инференс не влияет, проверено). Если конфликт станет блокирующим —
  раннер уже разделяет инференс и скоринг (`--rescore`), так что бэкенд можно гонять в отдельном venv.

### 2. Пакеты верхнего уровня в `src/` (`ocr`, `evaluation`, `text`, …)
* **Выбрано:** ровно структура из задания, чтобы работала команда `python -m evaluation.evaluate`.
* **Альтернатива:** один пакет-неймспейс `old_tatar_ocr.*`.
* **Риск:** общие имена (`ocr`, `text`) могут конфликтовать с чужими пакетами в общем окружении → используем
  отдельный `.venv`. Переименование в неймспейс — механическое, если понадобится.

### 3. Сегментация строк: kraken BLLA для всех line-распознавателей, с кэшем
* **Выбрано:** BLLA (стандартная модель kraken 7.1.1) с `text_direction=horizontal-rl`; полигональная
  вырезка строк kraken. Сегментации кэшируются (`OLD_TATAR_OCR_SEG_CACHE`), поэтому OpenITI-модели,
  PP-OCRv6, Phoenix и Azra получают **одинаковые строки** — сравнение изолирует качество распознавателя.
  Paddle/EasyOCR используют свои детекторы (это часть их «коробочного» качества), VLM (CHURRO) — страницу целиком.
* **Альтернативы:** свой детектор (YOLO и т.п.), Surya layout, Paddle layout.
* **Почему:** запрещено строить свой детектор без бенчмарка; BLLA обучена на исторических печати и рукописях
  и является стандартом eScriptorium/OpenITI.
* **Риски:** BLLA ошибается на двухколоночных словарях и таблицах (страницы 1927 г.); порядок чтения колонок
  влияет на CER страницы. Поэтому дополнительно считаем BoW-F1 (не зависит от порядка).

### 4. Порядок чтения для box-детекторов
* **Выбрано:** группировка боксов в визуальные строки по вертикальному перекрытию, внутри строки — справа налево.
* **Риск:** колонки читаются «поперёк» (строка левой колонки склеивается со строкой правой). Для baseline приемлемо,
  на двухколоночных страницах это видно в разнице CER vs BoW-F1.

### 5. Нормализация: хранение без потерь, сравнение по профилям
* **Выбрано:** `raw_ocr` хранится как выдала модель (только CRLF/BOM/внешние пробелы). Для метрик — профили:
  `nfc` (основной CER), `standard` («normalized CER»), `loose`, `arabic_only`. Каждое правило имеет ID и тест.
* **Альтернативы:** NFKC всего текста; одна «магическая» нормализация.
* **Почему:** kraken выдаёт NFD, разные модели пишут ی/ي/ى, ک/ك, ZWNJ или пробел — без нормализации CER
  измерял бы кодировку, а не чтение. Но нормализация с потерями недопустима для хранимого текста.
* **Риски (специфика татарского):** в яңа имля `ى`, `ە`, `ھ` — самостоятельные буквы; `standard` их сворачивает
  (Y1, H1). Поэтому всегда публикуем и `nfc`-CER. Буквы `ڭ/ݣ`, `گ`, `ۋ`, `ۇ/ۆ/ۈ` не сворачиваются ни в одном профиле
  (кроме K2: `ݣ`→`ڭ` — два способа записать ң).

### 6. Метрики
* CER/WER — микро-усреднение по корпусу (`Σ правок / Σ длины эталона`), Левенштейн по кодовым точкам после профиля.
  Значения > 100% не обрезаются (галлюцинации/повторы VLM должны быть видны).
* Отдельно: printed / handwritten, по `source_id`, по `script_style`, по `subset` (core/mixed).
* `exact_line_accuracy` реализована, но не применяется: нет построчного GT, совпадающего с сегментацией.
* BoW-F1 — отделяет ошибки распознавания от ошибок порядка чтения.

### 7. Предобработка выключаемая и логируемая
* **Выбрано:** YAML-конфиги `original` (только EXIF), `scan`, `mobile`; каждый шаг пишет лог; исходное изображение не меняется.
  Бинаризация по умолчанию выключена (уничтожает точки/огласовки — критично для арабицы).
* **Риск:** deskew по проекционному профилю ошибается на страницах с иллюстрациями/таблицами (порог 0.3°).

### 8. CHURRO на CPU через llama.cpp (GGUF)
* **Выбрано:** `mradermacher/churro-3B-GGUF` Q4_K_M + mmproj Q8_0, бюджет изображения 1.6 Мп (2048 визуальных токенов).
* **Альтернативы:** transformers bf16 (эталон; 7.5 GB весов не помещаются с запасом в 13 GB RAM вместе с ОС);
  Q8_0 + f16 mmproj (почти без потерь, но 4.6 GB при скорости сети ~0.3 МБ/с).
* **Риски:** квантизация и уменьшенное разрешение могут занижать качество CHURRO относительно опубликованного;
  результат помечен в `model_version`, эталонный путь `churro-hf` оставлен для GPU-машины.

### 9. Схема результата и запрет скрытой коррекции
`raw_ocr` никогда не правится языковой моделью. Поля `corrected_ocr`, `modern_tatar`, `translation`
зарезервированы и в Phase 1 равны `null`/`{}`. Любая будущая пост-коррекция пишет в своё поле.

### 10. Приватность
CLI не сохраняет изображения; раннер читает файлы бенчмарка только с диска. Ни один бэкенд baseline
не отправляет изображения третьим лицам (Transkribus и коммерческие API не подключены именно поэтому).
Загрузки — только весов моделей (Zenodo, Hugging Face) с проверкой checksum.

## Известные ограничения
* Только печатные источники в бенчмарке; рукописных старотатарских страниц с GT нет.
* GT — «silver» (Wikisource, большей частью уровень «не вычитано»).
* Двухколоночные/табличные страницы (словарь 1927, списки слов 1925) читаются с ошибками порядка.
* Уверенности разных движков не откалиброваны и не сравнимы между собой.
