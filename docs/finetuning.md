# Phase 3. Дообучение (fine-tuning)

> **Статус (2026-11-02): конвейер готов и проверен техническим прогоном; настоящее дообучение заблокировано
> отсутствием проверенных людьми обучающих данных.** Все 45 страниц с GT — тестовый набор; 12 пилотных страниц
> Phase 2 — машинные черновики. Обучение на черновиках = обучение модели на её же ошибках, а выдумывать разметку
> ТЗ запрещает. Первый реальный эксперимент запускается одной командой, как только выполнено «условие старта» ниже.

## 1. Две стратегии (ТЗ §15)

| критерий | **A: line-level CTC (kraken)** | **B: LoRA/full на VLM** |
|---|---|---|
| кандидаты | PP-OCRv6 medium (Apache-2.0), OpenITI Ottoman (CC0) | Azra-1-Mini 0.8B (Apache-2.0), CHURRO-3B (Qwen Research — некоммерч.) |
| CER до дообучения | ppocrv6: norm. CER 19.6% (1915), 58.9% / 61.7% (1925/1927) | не измерено (Phase 1 не завершена) |
| CER после | нет данных | нет данных |
| VRAM / RAM для обучения | CPU достаточно; 34.7 M параметров в режиме обучения | Azra LoRA: ~6–8 GB RAM на CPU (медленно) или GPU ≥ 8 GB; CHURRO LoRA bf16 ≥ 16–24 GB VRAM, QLoRA 4-bit ~10 GB |
| время обучения | см. технический прогон ниже (CPU) | на этой машине — часы на десятки строк (оценка), практично только с GPU |
| инференс | ppocrv6 на CPU: медиана 42.8 с/стр. (вкл. сегментацию) | CHURRO GGUF на CPU: минуты/стр. (оценка); Azra — построчно |
| размер модели | 64 MB (ppocrv6 medium), 16 MB (OpenITI) | 1.7 GB (Azra), 7.5 GB bf16 / 2.8 GB Q4 (CHURRO) |
| коммерческая лицензия | да (Apache-2.0 / CC0 + лицензия наших данных) | Azra — да; CHURRO — **нет** |
| печать | да | да |
| рукописи | PP-OCRv6 обучен и на рукописях | да (CHURRO — сильнее всего на рукописях) |
| риски | нужна построчная разметка (полигоны), BiLSTM/CTC чувствителен к сегментации | галлюцинации/повторы, медленно, тяжело воспроизводить |

**Решение для первого эксперимента: стратегия A на базе PP-OCRv6 medium**, контроль — OpenITI Ottoman.
Причины: лучшая из измеренных моделей, работает на имеющемся CPU, коммерчески чистая, разметка Phase 2
(PAGE XML) идёт прямо в тренер. Стратегия B — отдельный эксперимент при наличии GPU (решение владельца).

## 2. Протокол

1. Сначала только печать иске имля → затем смешанная печать (яңа имля, газеты) → затем рукописи;
   сложные рукописные примеры не смешиваются с первой тренировкой без отдельного эксперимента (ТЗ §15).
2. Данные: только `gold_verified`/`silver_proofread` страницы с PAGE XML, split из манифеста
   (по источникам и семействам); тест никогда не попадает в обучение (проверяется в коде и тестах).
3. Гиперпараметры по умолчанию: `lr=1e-4`, AdamW, постоянный LR, ранняя остановка по val (`lag=5`),
   аугментация вкл., `batch_size=1` (батчинг меняет вывод kraken), нормализация NFD как у базовых моделей,
   `--resize union` — алфавит расширяется татарскими знаками (ڭ ۋ ࢭ …).
4. Оценка — тем же раннером, что и baseline (`kraken-custom` бэкенд, одинаковые страницы `core`/`all`),
   плюс кривая обучения: 5 / 10 / 25 / 50 / все страницы (вложенные подвыборки, стратифицированы по источникам).
5. Каждый прогон: `models/finetuned/<name>/config.yaml` (команда, хэш базовой модели, версия датасета,
   гиперпараметры, seed, git, железо, версии библиотек) + `ketos.log` + `results/kraken-custom/<run>/`.

```bash
python scripts/finetune_kraken.py --name ppocrv6-oldtatar-v1 --base ppocrv6-medium --evaluate core
python scripts/finetune_kraken.py --name ottoman-oldtatar-v1 --base openiti-ottoman --evaluate core
python scripts/learning_curve.py --base ppocrv6-medium --sizes 5 10 25 50
```

## 3. Условие старта первого реального эксперимента (E4)

* ≥ 30 проверенных печатных страниц (иске имля) из ≥ 5 train-источников разных семейств;
* ≥ 6 страниц val из ≥ 2 других семейств;
* тест — существующие семейства (Татар мәктәбе 1915, Корбангалиев 1920-х).

Оценка трудозатрат: предразметка kraken-ppocrv6 даёт средн. уверенность 0.87–0.97 на пилотных страницах;
исправление черновика печатной страницы (~25 строк) — ориентировочно 10–20 мин. 30+6 страниц ≈ 1–2 рабочих дня
разметчика. Фактическая цифра будет измерена: `import_annotations.py` печатает CER «черновик → исправлено».

## 4. Технический прогон (synthetic smoke test)

Цель — проверить конвейер «PAGE XML → ketos → модель → оценка», **не качество** модели на старотатарском.
Данные: синтетические страницы (Amiri, libraqm), текст — из черновиков train-семейств (тестовые тексты не
используются). Модели технических прогонов — не результаты и в отчётах не сравниваются с baseline.

```bash
python scripts/finetune_kraken.py --synthetic-smoke --smoke-lines 36 24 --name smoke --max-epochs 3 \
    --min-epochs 3 --quit fixed --no-augment
```

## 5. Журнал Phase 3

| дата | эксперимент | итог |
|---|---|---|
| 2026-11-02 | smoke #1: ppocrv6-medium, ранняя остановка, параметры ppocrv6 по умолчанию | **упал** в kraken 7.1.1: AdamW+Muon + cosine требует известного числа шагов → `OverflowError: int(inf)`. Исправлено: AdamW + constant LR при ранней остановке |
| 2026-11-02 | smoke #2: 120 синт. строк train / 24 val, AdamW lr 1e-4, аугментация | конвейер замкнут: PAGE XML → ketos → чекпойнт → `ketos convert` (без потерь: 67.77% = 67.77%) → `kraken-custom` читает реальную страницу. **Скорость: 9 мин 08 с на эпоху (≈4.6 с/строку, CPU 16 потоков).** **Качество на синт. val после 1 эпохи упало: 95.7% → 67.8%** (ketos test, эталонные полигоны) — рецепт портит предобученную модель. Также: при `-q early` ketos игнорирует `-N` (эпохи «0/∞») — для коротких прогонов нужен `-q fixed` |

### Выводы технического прогона
1. **Конвейер работает от начала до конца** (данные → обучение → веса → оценка тем же раннером).
2. **Рецепт по умолчанию небезопасен:** AdamW с lr=1e-4 сразу ухудшает PP-OCRv6 (вероятная причина —
   случайно инициализированная NRTR-голова, +18 M параметров при обучении, чьи градиенты в начале портят общий
   backbone). Сравнение трёх рецептов (AdamW 1e-4; AdamW 1e-5 + warmup; AdamW+Muon + cosine, по 3 эпохи на
   36/24 синт. строках) **запущено, результаты ещё не получены** — будут добавлены в журнал. Реальное
   дообучение — только с рецептом, который на синтетике не ухудшает базу.
3. **Стоимость на этой машине:** ≈4.6 с на строку за эпоху. Пилот на 30+6 страницах (~900 строк) ≈ 1.2 ч/эпоху
   (10 эпох — ночь); 5 000 строк ≈ 6.4 ч/эпоху → для масштаба нужен GPU (на GPU ожидаемо в десятки раз быстрее).
